# Оптимізація прошивки — 2026-09-07

## Внесені зміни

- UART `get_config` / `AMCFG GET`: замість постійного буфера повного JSON — два проходи серіалізації одного документа. Перший рахує довжину та CRC32, другий надсилає ті самі HEX-пакети по 64 байти. Порядок полів, нумерація, контрольна сума та повідомлення початку/кінця збережені. `get:config` залишається сумісним.
- HTTP JSON: буфер на 256 байтів об’єднує дрібні записи. Часткові записи продовжуються з правильного зміщення; нульовий/помилковий запис закриває клієнта, щоб неповна відповідь не виглядала завершеною. Повний додатковий JSON-рядок не створюється.
- Завантаження старої конфігурації: повторне використання пулу парсера для канонічної серіалізації замість другого одночасного JSON-документа. Валідація, нормалізація, міграція і CRC не змінюються.
- LED: усі шляхи запису використовують спільне порівняння кадрів. Змінений кадр передається негайно в межах чинного розкладу анімації, незмінений — повторюється раз на 250 мс. Повтор потрібен для відновлення світлодіодів після окремого збою їхнього живлення. Початкове гасіння примусове. Кольори, яскравість, анімації й калібрування збережені.

## Виміряний результат

Порівняння з попередньою перевіреною збіркою після аудиту стабільності:

| Платформа | Статична RAM до → після | Звільнено RAM | Flash до → після |
| --- | --- | --- | --- |
| ESP32-C3 | 63 988 → 59 844 байти | 4 144 байти | 961 378 → 963 920 байтів |
| ESP8266 | 52 764 → 49 140 байтів | 3 624 байти | 467 243 → 468 859 байтів |

Flash трохи збільшився через додаткову логіку; образи залишаються в межах наявних розділів. Дані RAM — звіт компонувальника, а не пікова потреба всіх підсистем.

Тест із лічильником виділень пам’яті підтвердив пік JSON-пулів під час міграції: 5 632 байти на ESP8266 та 6 144 байти на ESP32-C3, без другого одночасного документа на 3 584 / 4 096 байтів.

У перевіреному прикладі HTTP-відповідь розміром 660 байтів передається за 3 блокові виклики. Це вимір кількості викликів до клієнта, а не кількості TCP-пакетів чи гарантія прискорення мережі.

## Перевірки

- Обидві прошивки успішно зібрані PlatformIO з чинними зафіксованими залежностями.
- Новий `tests/optimization_test.py` виконується для обох платформ у 32-бітному режимі: відповідність UART байт/CRC/порядку пакетів; межі 64-байтових блоків, UTF-8 та екранування; HTTP з нормальними, короткими й відмовними записами; збереження полів і контроль пікової RAM при міграції; LED зміни/незмінність/примусове оновлення/переповнення `millis()`.
- Пройдено `storage_fault_injection.py`: 877 переривань файлових операцій, відновлення temp/backup, CRC, короткі записи й відмови flush/rename, відкат та синхронізація Wi-Fi; також тести reset trace.
- Пройдено `runtime_regressions.py`: MQTT/DNS/дедлайни/валідація, 72 переривання запису знімка, UART, яскравість і звук.
- Пройдено `wifi_runtime_test.py`, `provision_ui_test.js`, `validate_config_contract.py`.
- Нову перевірку оптимізацій додано до Firmware CI.

## Перевірка підключеного ESP32-C3

Пристрій на COM7 (hostname `alarm-9E248C`) прошито з резервною копією та відновленням конфігурації. LittleFS не перепрошивався, оскільки вебфайли не змінювалися.

На фізичній платі отримано 511 байтів конфігурації у 8 HEX-пакетах, перевірено послідовність і CRC32 незалежно через Python `zlib`; весь JSON збігається з копією. Окремо перевірено сумісний `get:config`.

Надана користувачем Wi-Fi-конфігурація збережена й підтверджена читанням без виведення пароля. Під час перевірки стан залишався `wifiConnected=false`, IP точки налаштування — `192.168.4.1`. Підключення до роутера не підтверджено; очікується перевірка доступності мережі 2,4 ГГц. Це спостерігалося і до оптимізації. Через відсутність LAN-з’єднання HTTP на фізичній платі ще не перевірений.

Фізичного ESP8266 не було підключено. Тести не замінюють тривалих радіо/живлення-випробувань обох плат; фактичні колір і звук апаратно не вимірювалися.
